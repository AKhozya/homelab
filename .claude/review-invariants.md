# Review invariants

For any pre-commit reviewer (opposite-family peer static loop — see AGENTS.md; the cavecrew pre-push gate this file originally served was retired 2026-06-29). The reviewer already enforces CLAUDE.md hard invariants (image pin, every-ingress-has-NetworkPolicy, NP-port=container-port, DB-username=app, SOPS secrets, RoRFS+/tmp, GitOps-only) + CI (yamllint, kubeconform, shellcheck, gitleaks, sops-check, init-resources, image-pin) and catches generic bugs (selector≠template, off-by-one) unaided. This file covers what those miss. Flag real instances only; cite file:line. Verify name/GVK claims by grepping the target file before flagging.

## Established patterns — deviation is a smell

- App = flat single dir `apps/<app>/` — all manifests in one place (namespace, serviceaccount, deployment, service, storage, networkpolicy, ingress, certificate, secrets, provisioning jobs, kustomization). The repo-wide `base/`+`staging/` overlay split was fully collapsed (F-13 apps 2026-05-29, F-14 controllers, configs 2026-06-04); a NEW base/staging split is now the smell, not the norm.
- Namespace = bare app name (`mealie`, `immich`); kustomization sets top-level `namespace:`, children omit it.
- Mandatory pod label `app` OR `app.kubernetes.io/name` (Kyverno require-labels — **Enforce** since 2026-07-03, along with require-non-root and require-seccomp-runtimedefault: a mislabeled pod IS blocked at admission now, not just flagged in PolicyReports). Hand-rolled apps use `app: <app>` as the selector label, not `app.kubernetes.io/*`.
- Ingress middleware chain, ordered: `traefik-redirect-https@kubernetescrd,traefik-security-headers@kubernetescrd,traefik-rate-limit-{standard|high-frequency}@kubernetescrd,traefik-csp@kubernetescrd`. authentik gets NO rate-limit (breaks auth flow). `ingressClassName: traefik`, host `<app>.h0melab.work`, `tls.secretName: <app>-tls-secret` backed by `certificate.yaml`.
- "Dual access" is NOT a second Ingress object — internal = Traefik Ingress; external = a hostname row in centralized SOPS `infrastructure/configs/cloudflare/cloudflared.yaml` + an extra NetworkPolicy ingress from-block (`cloudflare-tunnel` ns). A second Ingress manifest for external is wrong.
- NetworkPolicy name `<app>-network-policy`; `podSelector.matchLabels.app: <app>`; `policyTypes: [Ingress, Egress]`. Ingress from-blocks (all on the container port): `traefik`, `cloudflare-tunnel` (if external), `uptime-kuma` (probe — not `monitoring` ns), same-ns `podSelector: {}` if a provisioning Job calls the app. Egress: DB→`databases` scoped `podSelector cnpg.io/cluster: main-postgres` TCP/5432; outbound HTTPS TCP/443 (bare in baseline — RFC1918 `except` is a per-app hardening, see Networking failure-modes).
- **DNS egress is NOT in the per-app NP anymore (R5, 2026-05-29 `6229d4ed`+`611b6320`).** The 14 standard apps get DNS from the shared component `apps/components/allow-dns-egress` (egress-only NP, UDP/53→`kube-system`), wired via `components:\n  - ../components/allow-dns-egress` in the app's kustomization. So: a standard per-app NP MISSING a DNS egress block is CORRECT, not a bug — do NOT flag it; and re-adding a per-app DNS block is the regression (duplicates the component). homehub + linkwarden's meilisearch keep `egress: []` (DNS solely from the baseline). EXCEPTIONS keep their own DNS and are NOT wired: `blocky` (kube-dns podSelector + DoT 853 + public resolvers) and `obsidian` (ns-wide `podSelector: {}` NP that also feeds its `couchdb-init` Job's DNS).
- **An egress NP isolates Job pods.** Any NP with `policyTypes:[Egress]` selecting a pod flips it from unrestricted→deny-except-listed. The `allow-dns-egress` baseline deliberately EXCLUDES Jobs via `podSelector.matchExpressions:[{key: batch.kubernetes.io/job-name, operator: DoesNotExist}]` (canonical label on K3s ≥1.27) so the 6 egress-naked provisioning Jobs aren't clamped to DNS-only. A ns-wide `podSelector:{}` egress NP that forgets this exclusion silently breaks Jobs on their next run — flag it.
- **A Job that needs egress gets its OWN egress NP (R5-followup `68dddceb`).** Selected by `batch.kubernetes.io/job-name: <job>` (NOT `app:` — Jobs don't carry the app label; a `app:`-selected NP matches zero Job pods = silent no-op, flag it), with DNS repeated (baseline excludes Jobs) + the one app CONTAINER port. Egress-only — the app ingress NP already admits the Job (don't demand a redundant ingress rule). 4/6 done (audiobookshelf-init/home-assistant-admin-setup/immich-admin-setup/n8n-user-provision). `mealie-user-provision`+`uptime-kuma-setup` stay naked by decision — they `apt-get`/`pip install` from the internet at runtime, so a tight NP is impossible without baking images (a 443→0.0.0.0/0 NP is theater — don't ask for one).
- DB role declared in CNPG `cluster.yaml managed.roles[]` (`ensure: present`, `passwordSecret.name: <app>-db-user`) BEFORE the app; secret `<app>-db-user` under `infrastructure/configs/databases/postgres/`, labels `cnpg.io/cluster: main-postgres` + `cnpg.io/reload: "true"`.
- Image variant suffix is load-bearing, match upstream's exact form: `-rootless`, `-fat`, `-standard-trixie`, or `vX.Y.Z` prefix. authentik pins tag + `imagePullPolicy: Always` (upstream re-publishes same tag).
- New-namespace app = 2-commit bootstrap: app added to `apps/kustomization.yaml` first; governance entry to `infrastructure/configs/resource-governance/kustomization.yaml` AFTER Flux creates the ns — avoids the apps→infra-configs circular dep.
- Provisioning Jobs annotate `kustomize.toolkit.fluxcd.io/force: enabled` + set `ttlSecondsAfterFinished`. Deployments set `revisionHistoryLimit: 2`. `startupProbe` when cold-start >30s (Django/Rails/Spring/Authentik).

## Failure modes schema/CI cannot catch

### Flux / Helm
- `healthChecks[]`/`dependsOn[]` must match a real name AND real apiVersion/kind — wrong GVK/name silently never matches → Kustomization stuck NotReady forever. (Wave 1: `vm-operator` vs `victoria-metrics-operator`)
- `dependsOn` only gates on the dependency's Ready condition, which requires `wait: true` or `healthChecks` ON THE DEPENDENCY — else readiness is never proven and ordering races admission. (Flux docs / F-7)
- `wait: false` + a `healthChecks` block = dead config, gates nothing. (F-8)
- HelmRelease without `upgrade.remediation.retries` (default 0) = a failed upgrade is left stuck with no auto-rollback. (Flux docs)
- Renaming a Kustomization with `prune: true` deletes+recreates ALL its workloads (set `prune: false` first); `force: true` delete-recreates any resource on immutable-field conflict (clusterIP, selector) = downtime — scope it. (Flux docs)
- Two other change shapes also prune, and neither is a rename: changing a rendered object's identity, and moving an object between Kustomizations. Read the dated records in `docs/HOMELAB_HISTORY.md` before approving either. 2026-07-03 "Deferred-item cleanup" covers the Redis-HA/CouchDB layer move. 2026-07-17 "Redis sentinel" covers the annotation that outlived it.
- **A `kustomize build` CLI failure is NOT proof a path is broken.** The Flux kustomize-controller auto-generates `kustomization.yaml` when absent at `spec.path` (recursive) + runs `LoadRestrictionsNone` (permits `../../` parent-escape refs) — so the bootstrap/root path (`clusters/`) + any `../../`-escape kustomization fail plain `kustomize build` (missing-kustomization / load-restrictor) yet reconcile fine. Before flagging a "deadlock"/wedge on a root-path or `spec.path` change, verify with `flux build kustomization <name> --path <p> --kustomization-file <f> --dry-run` (replicates the controller). Empirical check: if the cluster is *already* reconciling that path, it builds. (2026-06-12 `clusters/staging`→`clusters` flatten: cavecrew false-flagged a deadlock from a `kustomize build` failure; `flux build` exit 0 both paths refuted it.)

### Kyverno ValidatingPolicy (CEL) — sole policy engine since 2026-07-12 (kyverno.io/v1 CPs deleted)
- **CanAutoGen silent-kill** (CEL sibling of the retired CP `=()` footgun): a VP `matchConstraints` with ANYTHING beyond the single bare rule `[""]/["v1"]/["pods"]` (any excludeResourceRules, objectSelector, namespaceSelector, extra resourceRules) makes autogen silently die — controllers go unguarded, no error, `status.autogen` empty. ALL excludes belong in `matchConditions` CEL — UNLESS autogen is explicitly OFF (`autogen.podControllers.controllers: []`) with deliberate direct controller matchConstraints (require-non-default-serviceaccount, require-networkpolicy). Verify: `kubectl get vpol <name> -o jsonpath='{.status.autogen}'`. (kyverno 1.18 source, `pkg/cel/autogen`)
- **Autogen rewrites `object.metadata` to pod-TEMPLATE metadata in controller clones.** Namespace excludes MUST use `request.namespace` (never rewritten). Pod-LABEL excludes use `object.metadata.?labels[...]` — the template rewrite there is exactly what's wanted. But a `deletionTimestamp` / any top-level-metadata check is silently VOIDED in clones (template metadata never carries it — live-verified 2026-07-12, Codex catch): if the check must apply to the controller OBJECT, turn autogen off and match controllers directly (require-networkpolicy pattern).
- CEL optional-chain defaults must reproduce hard-anchor semantics: `c.?securityContext.?field.orValue(<fail-value>)` — for require-* checks the default must FAIL (e.g. `orValue(true) == false` for allowPrivilegeEscalation, `orValue(false) == true` for readOnlyRootFilesystem). An `orValue` that passes on absence is the CEL rebirth of the CP-era `=()` soft-anchor bug.
- Container-set parity is PER-POLICY, not generic: readonly-rootfs/drop-all-caps/privilege-escalation cover `ephemeralContainers`; resource-limits does NOT (k8s rejects resources on ephemeral containers); latest-tag/seccomp/non-root cover containers+initContainers only. Check git history of the CP twin before flagging a "missing" set.
- A "require X present" deny (require-networkpolicy) MUST scope `operations: ["CREATE","UPDATE"]` + skip objects carrying a `deletionTimestamp` — the webhook also fires on DELETE/finalization, so the deny blocks namespace teardown once X is pruned, wedging the ns in `Terminating` (csp-reporter incident 2026-07-03; fixes carried into the VP).
- A whole-namespace exclude in `matchConditions` on a PSS-privileged ns leaves host-namespaces/escalation fully unguarded there — prefer label-keyed object excludes. (F-38, CP-era class, still applies to VP ns-excludes. Actioned for `disallow-host-path` 2026-07-26 (B6-2): 5 ns replaced with 9 label-keyed identities. Measure before repeating it elsewhere — the other 4 policies exclude namespaces where **45-67% of pods genuinely violate**, so label-keying them means dozens of selectors against a Deny policy, more fragile than the hole it closes. B6-2 was worth it at ~15%.)
- **READ autogen, never RECONSTRUCT it** — `kubectl get vpol <name> -o json | jq .status.autogen`. Hand-reproducing the controller clones with `yq` to test them offline reproduces your *model* of the generator, and the tests then confirm the model instead of catching it. Cost 2026-07-26: a `yq`-built clone rewrote only `validations`, "proving" that pod-label matchConditions are copied verbatim and that CronJobs therefore need controller-level labels. Both false, five manifests changed for nothing.
- **A Kyverno CLI `skip` is ambiguous** — "excluded by matchConditions" and "never matched the resourceRule at all" print identically, so a clean `skip` is not evidence an exemption works. Pair every exemption case with a stripped-label control that must FAIL. Same false-clean class as the vmsingle/empty-result rule. (2026-07-26 B6-2)
- **Build admission probe pods from a REAL live pod spec**, not a synthetic one: the other 11 Deny policies reject a hand-written pod first and the webhook names only that policy, so the probe says nothing about the one under test. Corollary — overriding a label on a workload that carries other label-keyed exemptions (node-exporter's hostNetwork/hostPID/hostPort, alloy's privilege escalation) breaks *those* too; inject the violating field into an innocent running pod instead. (2026-07-26)
- Fine-grained VP webhooks (`vpol.validate.kyverno.svc-fail-finegrained-<policy>`) short-circuit: an admission response names only the FIRST failing policy, not all violated ones — per-policy probes needed for attribution testing (Gate B 2026-07-12).
- **New-namespace bootstrap needs 2 commits under require-networkpolicy.** Flux server-side dry-runs the WHOLE apply set before persisting anything, so a single commit shipping ns+NP+workload has the workload validated against a namespace whose NP doesn't exist yet → VP denies, kustomization stuck on the old revision. Reviewer check: any diff introducing a namespace AND a workload in it must split ns+NP(+SA/RBAC) → workload across two commits. (2026-07-14 trivy-scan, first new ns since VP migration)
- **Helm hook Jobs go through admission — a chart's hook without resource limits wedges every upgrade.** kube-prometheus-stack's pre-upgrade admission-webhook cert Jobs ship limit-less; require-resource-limits denied them → 87.15.2 AND 87.16.0 upgrades stalled (4 attempts, auto-rollback to 87.15.1) while the HelmRelease looked merely "not Ready". Reviewer check on any chart bump: does the chart run hook Jobs, and do values pin their resources (e.g. `prometheusOperator.admissionWebhooks.patch.resources`)? A stalled HelmRelease also silently holds back ALL later values changes riding the same release. (2026-07-14)

### NetworkPolicy
- AND/OR trap: `namespaceSelector` + `podSelector` under ONE `from`/`to` list item = AND; as SEPARATE list items = OR. One indent level turns "prometheus pod in monitoring ns" into "any pod in monitoring OR prometheus in ANY ns" — no API error. (CNCF / Apr 2026 n8n·linkwarden·mealie)
- `0.0.0.0/0` (or bare 443) egress without an `except:` for RFC1918 (10/8, 172.16/12, 192.168/16) lets a compromised pod reach cluster-internal services. (F-9 immich, F-11 n8n)
- DB-port egress (5432/3306/6379) must be scoped via `namespaceSelector` to `databases`, not `{}` (all-ns). (F-10)
- A pod selected for Egress with NO egress rule denies all egress including DNS → every lookup hangs ~30s (not "refused"). `namespaceSelector` matches namespace LABELS, not names — use `kubernetes.io/metadata.name`. (k8s docs)
- Cross-pod reachability is DUAL-SIDE: a client's egress to a DB/service pod is silently blocked unless the DEST pod's ingress NP ALSO has a matching `from`+port. A diff that adds a new client's egress (e.g. a 2nd exporter → a DB) but not a matching ingress on the target → kube-router **REJECT = "connection refused"** (fast, NOT the 30s DNS-style hang above; surfaces as `mysql_up=0`/connect errors, not lookup hangs). When a diff adds an exporter/client egress to an existing DB/service pod, confirm the dest's ingress NP gained a from-block for that source+port. (2026-06-07 mysql-replica-exporter→haproxy:3307)
- `hostNetwork: true` pods bypass NetworkPolicy entirely. (CNI docs)

### securityContext / PSS
- PSS Baseline forbids `hostPath` (its own control, independent of Restricted's volume allowlist) — a securityContext-clean pod still gets denied; a ns mounting hostPath (log collectors, backup Jobs) cannot drop below `privileged`. Prove a level change with `--dry-run=server` first. (F-45 — prior memory assumed the opposite)
- A PSS rejection leaves the Deployment "successfully applied" while the ReplicaSet silently fails to create pods — the violation surfaces only in ReplicaSet events, not Deployment status. (k8s docs)
- PSS Restricted needs `seccompProfile: RuntimeDefault` on the pod or EVERY container+init — one omission fails the whole pod; Baseline checks none of this. PSA is non-mutating (validates, never defaults) — relying on a defaulted field needs Kyverno mutate. (k8s docs)
- Don't delete a documented init/securityContext exclude — it resurrects a known crashloop. paperless-ngx s6-overlay needs the root `fix-permissions` init owning `/run` (else `CrashLoopBackOff: /run belongs to uid 0`). (incident ca3891c→d3b5036. Nearly deleted again 2026-07-26 — a violation scan that replicates a policy's own logic answers "does this PASS?", not "does this run as root?", and `require-non-root` passes on a pod-level `runAsNonRoot: true` regardless of container overrides. Caught by review, not by the scan.)
- **PSA evaluates BEFORE Kyverno and masks it.** A hostPath/privileged probe in a `restricted` or `baseline` ns is rejected by PodSecurity and never reaches the Kyverno webhook — so a denial there proves nothing about the Kyverno policy under test. Both PSS Baseline and Restricted forbid hostPath; only `privileged` admits it. Corollary: **any ns running a hostPath workload is `privileged`, so Kyverno is the sole guard there** — a ns-exclude in such a ns means zero enforcement, not defence-in-depth. (2026-07-26: monitoring/loki/databases/immich/backup-replication were all `privileged` AND Kyverno-excluded.)
- **`require-non-root` has a real container-override bypass.** Its first branch is a **pod-level** `runAsNonRoot` test, so a pod-level `true` satisfies the whole policy however an individual container overrides it — a root container passes. This is a live gap in every ns the policy actually matches, not an accepted exception: the known root workloads (paperless-ngx `fix-permissions`, mealie's provisioning Job) sit in namespaces that are ns-excluded anyway, so they are NOT what keeps the expression loose. Hardening it means auditing the matched namespaces, not the excluded ones. (2026-07-26; the "it would break paperless/mealie" rationale was wrong — Codex catch)

### Secrets / DB
- A plaintext secret literal in a ConfigMap where the app does NOT env-substitute (e.g. blocky `queryLog.target` parsed by pgx) — `.sops.yaml` encrypts only `^(data|stringData)$`, and sops-check guards `kind: Secret` only, so this leaks. Fix: a SOPS Secret with the literal inlined. (F-1 / blocky)
- A CNPG/Percona role must be in `Cluster.spec.managed.roles[]`, not just a labeled Secret → else `role does not exist (42704)` and the password is lost on PG restart. (linkwarden)
- An internal ingress missing the Authentik forward-auth middleware is exposed without SSO, not just unstyled. (F-37)
- **A rotated secret with a second copy outside Git keeps serving the old value.** SOPS is the source of truth, so the rotation commit reads as complete. A consumer holding its own copy has no reconcile loop and no drift alert. The mismatch then surfaces only as an auth error on whatever path uses it. `claude-telegram-env.trigger-secret` was rotated 2026-07-31; `/etc/node-maintenance/claude-trigger-secret` kept its April value, and the weekly maintenance trigger answered 403 on two consecutive runs before anyone noticed. Reviewer check on any secret change: grep the whole repo, `node-maintenance/**` and `scripts/**` included, for every consumer of that key. Prefer deleting the second copy over syncing it — read the value from the one place that already holds it. (2026-08-08)
- **A multi-document SOPS file carries ONE MAC over the whole file** — every document's `sops:` block holds the same `mac:`. Deleting a document by truncating the ciphertext yields `MAC mismatch` on the *survivor*. Anything that rewrites the whole file works — `sops edit <file>` interactively, or scripted: `sops -d` → drop the doc with `yq` → `sops -e --config .sops.yaml`. What fails is a partial edit of the ciphertext. Comments survive the round-trip. (2026-07-26, removing `alertmanager-basic-auth-credential`)

### Kustomize
- `commonLabels` mutates `spec.selector.matchLabels`, which is immutable on existing Deployments → `kubectl apply`/Flux fails. Use the `labels` transformer with `includeSelectors: false` for metadata-only labels. (Kustomize docs)
- `namePrefix`/`nameSuffix` auto-rewrites built-in name refs (Service selectors, configMapKeyRef) but NOT custom-resource refs, `patchesJson6902` targets, or external consumers — those break silently. configMap/secretGenerator append a content-hash suffix that breaks any consumer outside the same kustomization referencing a literal name. (Kustomize #972)

### RBAC
- **`patch` on a workload is `patch` on the whole pod template**, not on one annotation. RBAC has no
  verb for "may set `restartedAt`", so a grant added for `kubectl rollout restart` also permits
  rewriting `command`, `image`, `serviceAccountName` and volume mounts. Where that template carries
  a security control (the claude-telegram init sweep), the control becomes editable by the thing it
  constrains. `pods delete` achieves a restart with strictly less reach. (2026-08-06)
- **A binding in the workload's OWN namespace closes the loop.** Check whether an exec/jobs/patch
  RoleBinding lists the app's own namespace — that is how a workload reaches its own Deployment.
- **`kubectl auth can-i ... create pods/exec` returns a FALSE `no`.** The subresource form is
  `create pods --subresource=exec`. The slash form silently reports no access where access exists,
  so an RBAC change verified with it looks tighter than it is.

### Shell
- **In a safety check, a failed read must not become the permissive answer.** This is the recurring
  bug class in this repo's inline container shell, found five times in one script on 2026-08-06:
  `jq` exits **0** on EMPTY input and prints nothing, so a `kubectl` that exits 0 with an empty body
  yields "no pods" / "no budgets" / "not covered" — every one the allow answer. Gate every payload:
  `jq -e 'type == "object" and (.items | type) == "array"'` (exits 4 on empty, 1 on false; a real
  `.items: []` still passes, because "none" is an answer and `""` is not). Checking only the
  command's exit status is not enough.
- **`set -e` is suppressed inside a function invoked as a condition** (`if pred; then`), and for
  everything it calls — failures fall through to the function's final `return`. Compounding it, a
  helper that `exit 1`s inside `var="$(helper)"` only kills the subshell and leaves the caller
  running on an empty string. A predicate meant to fail CLOSED therefore returns "allowed" on any
  read error. Wrap each call as `if ! var="$(...)"; then return <blocked>; fi`; have helpers
  `return`, never `exit`.
- `A | grep -q X && echo Y || echo Z` — the pipe binds tighter than `||`, so the middle branch breaks; shellcheck misses the logic. Use `set -euo pipefail`, not bare `set -e`. (F-27 setup-node.sh, F-28 analyze-update.sh)
- **A notifier whose caller discards its exit code must alert on its own failure.** `ExecStopPost=/bin/sh -c '… /usr/local/sbin/notify.sh "…" || true'` is the standard shape in `node-maintenance/systemd/**`. The `|| true` is deliberate — a failed notification must not fail the unit. That makes the notifier the one program whose non-zero exit reaches nobody, so a broken notify path stays invisible. A 403 went unreported for two weekly runs. Reviewer check on any script a caller invokes under `|| true`, `failed_when: false` or `ignore_errors`: does it report its own failure through a different channel? An `echo … >&2` into a journal nobody reads does not count. (2026-08-08)
- **`kubectl delete pod <name>` is unsafe wherever the name is stable.** StatefulSet pod names are fixed (`<sts>-0`), so a listing that selected a terminal pod can be stale by the time the delete runs. If anything removes that object in between, the controller recreates a **Running** pod under the same name. A delete by name alone would then take the live pod. On a StatefulSet that is a DB primary, which `AGENTS.md` reserves for the CRD plus `kubectl rollout restart`. Carry the discriminator into the delete so the API re-tests it server-side: `kubectl -n <ns> delete pod --field-selector="metadata.name=$name,status.phase=$phase"`. Applies to any list-then-delete loop over pods, not only in ansible. (2026-08-08 Codex catch; the field-selector form was proved both ways against the live cluster.)
- **Backup/dump success-theater (embedded CronJob shell — invisible to CI shellcheck).** Three patterns make a partial/failed backup report success, and all alerting keys on job-exit-status so the loss is silent: (a) `cmd 2>&1 | tee file` under `set -e` **without** pipefail — the pipeline's exit is tee's (always 0), so a failed `pg_dump`/`mysqldump` never trips `set -e` and the following `if [ $? -eq 0 ]` tests tee, not the dump. Fix: `set -eo pipefail` + `if cmd | tee …; then` (the `if` keeps set -e from aborting mid-loop). (b) `mysqldump … > out.sql 2>&1` redirects **stderr into the dump file** — the `[Warning] Using a password…` line becomes line 1 and `mysql < out.sql` chokes at restore. Fix: `2>err` sidecar (or `MYSQL_PWD` to kill the warning). (c) a missing required input handled by a bare `continue`/warning that does NOT increment a failure counter → the job still exits 0 with a silent gap. Fix: count the failure + `exit 1` before packaging. (2026-07-03 ultrareview: postgres/mysql/pvc backup jobs all three.)
- **An rsync `--exclude`/`--include` pattern without a leading `/` matches at EVERY depth.** `--exclude='immich/'` drops `immich/` at the transfer root and also any `pvc/<ts>/immich/…` a future app might create — silently, with no error and no log line. Anchor anything meant for the root: `--exclude='/immich/'`. Reviewer check on any filter added to a backup/replication rsync: is the pattern anchored, and would an unanchored match hit a path the job is supposed to carry? (2026-07-27 Codex catch, proved both ways on a local fixture before shipping.)
- **Two jobs writing overlapping destination paths is a circular pipeline, not a tuning problem.** `sent <huge> bytes` with `speedup is 1.00` on a repeat run means the files genuinely were absent at the destination — look for a second job that prunes or owns that path before reaching for rsync flags. `backup-replication` re-uploaded 129G of immich generations nightly that its own keep-2 pruned minutes later, because `immich-backup` publishes that path itself. Rule: one job owns one destination path; replication excludes what another job publishes. (2026-07-27, `5f76db93`.)

### systemd units

Units ship from two trees — `node-maintenance/systemd/**` and
`node-maintenance/ansible/roles/*/files/*.{service,timer}`. Nothing in CI parses either.

- **A directive in the wrong section is accepted and dropped, and only the journal says so.** `StartLimitIntervalSec` and `StartLimitBurst` belong in `[Unit]`. Under `[Service]` systemd logs `Unknown key 'StartLimitIntervalSec' in section [Service], ignoring` on every reload and falls back to the 10s default. The retry cap the unit's own comment describes then never applies. Check the effective value against what the unit meant to set, not against the file text: `systemctl show <unit> --property=StartLimitIntervalUSec --property=StartLimitBurst`. A unit may legitimately configure the 10s default, so only the mismatch with intent proves the key was dropped. The warning sits in the journal for months and reads as noise. (2026-08-08, `node-maintenance-phase2.service` — the cap was inert from the day the unit shipped.)

### Traefik / Ingress
- **`rateLimit.average` is per `period`, default `1s`.** A middleware with `average: 100` and NO `period:` enforces 100 req/**second** (~6000/min), not the "100/min" the comment claims — 60× looser, so a brute-force/scrape never trips it. Fix: set `period: 1m` (or the intended window) alongside `average`. `burst` is instantaneous-concurrent, unrelated to the rate. (2026-07-03 ultrareview: both rate-limit-standard/-high-frequency were per-second.)

### Monitoring / VMRule
- **The vmsingle/empty-result rule: an empty query result is not evidence of "nothing firing".** `vmsingle` is a **Deployment** — `vmsingle-vmsingle-0` does not exist, so a `kubectl exec` against that name fails, writes to stderr, and a `2>/dev/null` on the pipeline turns the failure into empty stdout that reads as a clean alert list. Reach it by label (`-l app.kubernetes.io/name=vmsingle`) or `svc/vmsingle-vmsingle`, and assert `.status == "success"` before believing `.data.result` is empty. Applies to any probe whose "all clear" is the absence of output. (2026-07-26: masked two nights of failed CouchDB backups.)
- **A staleness alert `time() - <Job metric> > N` is structurally DEAD when N > the Job's `ttlSecondsAfterFinished`.** kube-state-metrics drops `kube_job_*` series when the Job is TTL-reaped (backups: 24h TTL), so a >24h threshold (e.g. 48h) can never be satisfied before the series vanishes — a "0 firing" scan looks healthy. Also a per-namespace `max(...) by (namespace)` masks one stopped CronJob when a sibling in the same ns still runs. Fix: key on the CronJob status metric `kube_cronjob_status_last_successful_time` (NOT TTL-reaped, persists on the Flux-managed CronJob object), evaluated per-cronjob. `_shared/vmrules-metric-audit.sh` now flags this class. (2026-07-03 ultrareview: NoRecentBackups.)
- **A schedule-miss alert `time() - kube_cronjob_next_schedule_time > N` FALSE-FIRES on non-daily CronJobs.** KSM computes `next_schedule_time = lastScheduleTime + interval`; a weekly (or monthly) CronJob — or any CronJob whose last run was off-slot/manual, which does NOT advance `.status.lastScheduleTime` — leaves that "next" time in the PAST for days, so a daily-tuned threshold (600s / 3600s) fires even while the job is healthy. Fix: exclude the known non-daily CronJob(s) by name (`cronjob!="immich-backup"`) and cover their staleness with a cadence-appropriate `kube_cronjob_status_last_successful_time` rule instead. Reviewer check: any new `CronJobNotScheduled`/`*MissedSchedule`-style rule must exclude every non-daily CronJob. (2026-07-03: immich-backup, weekly, tripped `CronJobNotScheduled` + `BackupCronJobMissedSchedule`.)
